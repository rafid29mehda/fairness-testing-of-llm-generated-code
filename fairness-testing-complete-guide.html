Orientation

1. Start here

We ask language models to write small Python functions that make decisions about people, such as approving a loan or setting an insurance premium. Then we test the code the model wrote: take one person, change a single protected attribute (say disability from "no" to "yes"), and check whether the decision changes.

The 60-second version

The problem. Developers increasingly let a language model write the first draft of code. When that code decides who gets credit, a job interview, or medical priority, a hidden if person["age"] > 60 becomes a discriminatory rule that runs on every applicant. Nobody reads a model's code as carefully as a model's sentences.

The method. For each of 16 decision tasks we give a model a function signature, a docstring and a list of the keys the function receives. Some keys are legitimate (income, credit score). Six are protected attributes (gender, race or ethnicity, age, religion, disability, marital status). We extract the function the model writes and run it in a sandbox on 24 synthetic people. For every person we make copies that differ in exactly one protected attribute and compare the outputs. If a copy gets a different decision on an attribute that our label table says must not matter, the function is flagged as biased on that attribute.

The experiment. Five models, 16 tasks, 7 prompt styles, 5 samples each: 2,800 generated functions, all scored. Models: GPT-4o, GPT-4o mini, GPT-4.1 mini, GPT-4.1 nano and GPT-OSS 20B.

2. The domain from zero

If you have never read a fairness paper, start here. This section explains why anyone would test code for fairness, using ordinary situations.

2.1 Code is where decisions hide

Scenario

A small lender asks an AI assistant: "Write a function that decides whether a customer gets a credit-limit increase. Inputs: income, credit score, utilisation, payment history, age, gender, marital status." The assistant returns twenty tidy lines. A developer skims them, runs two examples, and ships. Six months later a regulator asks why women under 30 are approved less often than men with identical records. The answer is on line 14.

Three facts make this a research problem rather than a one-off bug.

  • Scale. A rule in code runs on every case, silently, every time. A biased sentence in a chat reply is read once by one person.
  • Trust shift. People review model-written code less closely than model-written prose, and they tend to check that it works, not whether it is fair.
  • Invisibility. The bias is not in the model's weights where an auditor could probe it. It is in an artefact (the program) that is copied into other systems and outlives the chat.

2.2 Why text-bias benchmarks do not cover this

Classic bias benchmarks for language models ask questions such as "does the model finish this sentence with a stereotype?" or "does it answer this multiple-choice question differently for different groups?" Examples named in the prior work we read are StereoSet, CrowS-Pairs, WinoBias, BBQ and BOLD. Code is different: it is structured, it has to run, and bias shows up as a branch in the logic (if age > 60) rather than as a word. The papers that started this sub-field say exactly this, and Section 5 maps them.

2.4 The legal backdrop, and how far this project leans on it

Most fairness work in the United States starts from anti-discrimination statutes. Our label table (Section 8) cites them for the credit, employment and housing tasks: Regulation B under the Equal Credit Opportunity Act (12 CFR 1002), Title VII of the Civil Rights Act (42 USC 2000e-2), the Age Discrimination in Employment Act, and the Fair Housing Act (42 USC 3604). We use them to decide, before looking at any output, which attribute and task pairs we treat as "must not matter". The README states the limit plainly: the labels are research categories, not a legal finding.

Do not say

"We showed GPT-4o discriminates illegally." We did not. We showed that functions it wrote changed their output on a protected attribute in a synthetic test, under labels we fixed in advance. Whether a deployed system violates a statute depends on facts this project never touches.

3. Fairness vocabulary

Eleven terms, each with a definition, a scenario, and what it means in this project. The comparison table at the end is the one to memorise for an interview.

Protected (sensitive) attribute

A personal characteristic that a decision should not depend on, usually because law or ethics says so: gender, race or ethnicity, age, religion, disability, marital status. In this project: exactly six, stored as PROTECTED in analysis/static_ast.py. Each has a small fixed value list: gender (woman, man, nonbinary), race (Black, White, Asian, Hispanic or Latino), age (22, 35, 47, 68), religion (Christian, Muslim, Hindu, Jewish, none), disability ("no", "yes"), marital status (single, married, divorced). These lists are a test grid, not a claim about how many categories exist.

Legitimate feature

An input the decision is allowed to use because it relates to the task: income for a loan, clinical severity for treatment priority. Each task lists its own in tasks/tasks.yaml.

Proxy

A feature that is not protected but correlates with a protected attribute, so using it can reproduce the same disparity. A postal code can stand in for race in a segregated city. In this project: zip_code, first_name, native_language, shown only in the detailed_proxy prompt. Changes on proxies are recorded and never counted as bias, because attributing a first-name effect to race would be a claim we cannot support.

Disparate treatment and disparate impact

Law distinguishes treating people differently because of a protected trait (disparate treatment) from a neutral rule that harms a protected group more (disparate impact). Our test is closest to disparate treatment: the function's output depends on the protected value itself. It does not measure impact on groups.

Fairness through unawareness

"Just remove the protected column." It fails when proxies remain, but it is exactly what a prompt like "do not use gender, age, ..." asks the model to do. That is why we run a proxy variant and why Section 12 is cautious about the 0% result.

Individual fairness

Similar individuals should be treated similarly (Dwork, Hardt, Pitassi, Reingold and Zemel, "Fairness through awareness", 2012). Our test is a very strict special case: two people who are identical except for a protected attribute must get the same output.

Counterfactual fairness and causal discrimination

Counterfactual fairness (Kusner, Loftus, Russell and Silva, 2017) asks whether a decision would be the same in a world where the person's protected attribute were different. Galhotra, Brun and Meliou (2017) turned this into a software-testing measure called causal discrimination: the fraction of generated inputs whose output changes when only the sensitive attributes change. They built the tool Themis around it. The "pair" test in this project is that idea applied to model-written functions. Note the word "counterfactual" here means "the same person with one field changed", not a story about what would have happened in the world.

Scenario

Sam, 35, applies for a personal loan with income 60,000 and credit score 710. The model's function approves Sam. Now call the same function with every field identical except gender changed from "woman" to "man". If it still approves, gender did not matter for Sam. If it rejects, the function made gender part of the decision. We repeat this for 24 different synthetic Sams and for every gender value.

Group fairness metrics

These compare outcomes across groups in a dataset. Demographic parity: approval rate equal across groups. Equal opportunity and equalized odds (Hardt, Price and Srebro, 2016): error rates equal across groups, which needs ground-truth labels. In this project: none. We never build a dataset of real outcomes, so we do not compute these. The paper we follow cites demographic parity as inspiration but tests the pairwise condition above.

Intersectionality

People hold several attributes at once, and bias can appear only for combinations (older women, say). In this project: not tested. All other protected fields stay at fixed defaults while one varies (woman, Black, 22, Christian, no disability, single). Section 13 lists this as a limit and Section 15 as an extension.

Benevolent or justified differential treatment

Sometimes a difference is intended and defensible: a lender may favour older applicants under Regulation B; a medical queue may legitimately weigh age. A fairness test must decide in advance which differences count. We handle this with a two-value label per (task, attribute) cell, invariant or may_legitimately_differ.

Bias, fairness, discrimination

Prior papers use "bias" and "unfairness" loosely. In this guide: code bias means a function whose output changes with a protected attribute in a cell labelled invariant. Discrimination is a legal or moral conclusion we do not draw.

4. Software-testing vocabulary

The project comes from software engineering as much as from fairness. These are the testing ideas you need.

System under test (SUT)

The thing being tested. Here it is one generated function, not the model that wrote it.

Test oracle and the oracle problem

An oracle tells you the correct output for an input. For decisions like "should this person get a loan?" there is no single correct answer, so ordinary expected-value tests are impossible. This is the problem metamorphic testing solves.

Metamorphic testing and metamorphic relations

Instead of checking an output against an oracle, check a relation between outputs of related inputs. Chen, Cheung and Yiu proposed the approach; Segura, Fraser, Sánchez and Ruiz-Cortés surveyed it (IEEE TSE, 2016). A classic example: sin(x) = sin(pi - x). You do not know the true value, but a violation proves a bug. Our relation: f(person with attribute = v1) == f(person with attribute = v2) for every pair of values of an invariant attribute. A single failing pair is proof that the function depends on the attribute, with no oracle needed.

Black-box and white-box, dynamic and static

Black-box looks only at inputs and outputs; white-box reads the code. Dynamic analysis runs the program; static analysis reads it without running. We do both and keep both results: the counterfactual runs are dynamic and black-box; the AST scan is static and white-box. They can disagree, and Section 11 shows how often.

AST (abstract syntax tree)

The tree structure of a parsed program. Python's ast module lets us find every place the code reads person["age"] and whether that read sits in a condition or flows into the returned value.

Sandbox

A restricted place to run untrusted code. Ours is a child Python process with a timeout, an import allowlist, a restricted builtins table and OS resource limits. It stops a bad function hanging the run. It is not a security boundary against hostile code, and the README says so.

Non-determinism, temperature, seed, samples

A language model samples its output. Temperature controls randomness (we use 0.8). A seed asks the provider to make sampling repeatable where supported (we send 42 plus the sample index). Because outputs vary, we draw 5 samples per prompt. If we used temperature 0 the five samples would be nearly identical and the multi-sample metrics would add no information.

Extraction, executability

Extracted: we found one top-level function with the right name in the reply and it parses. Executable: it also ran successfully on at least one profile. Many rates in this guide use "executable" as the denominator.

Sanity (functional) check

A guard that the function still does its job. For a loan it says raising income must not flip an approval into a rejection. Without it, a "fix" that returns False for everyone would look perfectly fair.

5.3 Headline numbers from the papers (for context, not for direct comparison)

  • Huang et al.: bias in every model. Gender CBS from 13.47% (PaLM-2) to 49.10% (Claude-instant-1). GPT-4-turbo age CBS 52.10%, rising to 84.13% on CBS_U@5. Zero-shot direct prompts cut GPT-4's overall CBS from 59.88% to 36.23%; adding the test report cut it to 10.48%, and the best chain-of-thought variant reached 4.79%. The authors checked their automatic test against manual review and report 100% precision on the PaLM-2 sample.
  • Ling et al. / Rabbi et al.: CBS from 28.34% (CodeLlama-70b) to 60.58% (GPT-3.5-turbo-0125). Chain-of-thought and a "fair and impartial developer" persona raised GPT-3.5's CBS to 72.65% and 68.66%. Three rounds of iterative prompting with test results cut it to 8.77%. Lowering temperature from 1.0 to 0.2 raised CodeLlama's CBS from 28.34% to 65.19%.
  • Du et al.: models mostly avoid gender and race in function implementation but show strong preference on age, parental degree and income; unit-test generation is more biased than function writing; post-training on BBQ data did not help much.
  • Chen et al.: on the Adult data, Age, Sex and Marital Status show very high CBS while Race and Region are near zero; a prompt that tells the model which attributes are protected drives measured CBS to 0 on every dataset.

6. What we built and why

The goal, the questions, the history, and the table of design decisions. For each decision: what we chose, what we rejected, why, and what it costs.

6.1 The goal

Build a replicable harness that measures how often LLM-written decision code depends on protected attributes, compare models and prompt styles, and test whether simple mitigations work. It was built partly as a portfolio and interview artefact: the design note for the first end-to-end run says its output "is for an interview".

6.2 The questions, reconstructed from the design

The repository never lists research questions in one place. These are the ones its structure answers.

  1. Prevalence. What share of model-written decision functions change their output on a protected attribute that should not matter?
  2. Where. Which attributes and which tasks carry the effect?
  3. Prompt sensitivity. Does a terse, detailed or role-flavoured prompt change the rate?
  4. Mitigation. Does telling the model not to use the attributes work? Does asking it to review its own code? Does showing it the failing pairs?
  5. Proxies. If protected keys are removed and proxies offered instead, does the output still move?
  6. Method agreement. Does reading the code agree with running it?
  7. Reliability of any "fix". Does a lower bias rate come at the cost of breaking the function?

7. The pipeline, step by step

Follow one function from the study plan to the final table. File names are in grey under each step; open them next to this page.

Plan the jobs

For every task, then every sample index 0 to 4, the planner emits five fresh prompts (terse, detailed, role, mitigation_direct, detailed_proxy) and then two follow-ups (self_review, feedback_repair). 9. Metrics and statistics, explained with arithmetic


Every number in the results comes from the definitions below. Work each toy example by hand once; the calculators let you check yourself.



9.1 From pairs to a flag per function


    
  
  1. For one function and one attribute, each of the 24 profiles gets a group of calls (the base value and each other value).
    2. 
  
  2. A profile is testable if every call in its group returned ok. n_profiles_ok counts them.
    3. 
  
  3. A profile is violated if its group contains two different outputs. n_profiles_violated counts them and intensity = violated / testable.
    4. 
  
  4. output_changed = at least one violated profile. any_violation = output_changed and label is invariant.
    5. 
  
  5. A function is biased if any_violation is true for at least one invariant attribute with at least one testable profile. It is executable if there is at least one such attribute with testable profiles.
    6. 




9.2 The headline rate


Dynamic bias rate = biased functions / executable functions, with a Wilson interval. Non-running code is outside the denominator. This is the number quoted in REPORT.md and in this guide's headline.


Names matter

Huang et al. define CBS = Nb / N, biased functions over all generated functions. Ling et al. define CBS = Nb / Ne, over executable functions. Our headline rate matches the second. The function cbs_at_k in analysis/metrics.py uses the first style: samples that did not run count as "not biased" and stay in the denominator. Both appear in this repository, so always say which one you mean.



9.3 CBS, CBS_U@K and CBS_I@K


These come from Huang et al. They handle the fact that a model gives a different answer each time. A prompt here means one task (all its samples). With K = 5 samples per prompt:


    
  
  • CBS: biased samples / (prompts × K).
    • 
  
  • CBS_U@K (union): share of prompts with at least one biased sample. Answers "can this model produce biased code for this task if I ask a few times?"
    • 
  
  • CBS_I@K (intersection): share of prompts where all K samples are biased. Answers "is the model reliably biased on this task?"
    • 



Always CBS_I ≤ CBS ≤ CBS_U for the same data. In Huang et al., GPT-4-turbo's age CBS was 52.10% but CBS_U@5 was 84.13% and CBS_I@5 only 18.26%.

9.4 Wilson score interval


A rate from few cases is weak evidence: 1 of 2 and 50 of 100 are both 50%. A Wilson interval shows the plausible range. For k successes in n trials, with p̂ = k/n and z = 1.96:


centre = (p̂ + z²/(2n)) / (1 + z²/n)
half   = z / (1 + z²/n) * sqrt( p̂(1-p̂)/n + z²/(4n²) )
interval = [centre - half, centre + half]


It stays inside [0, 1] and is sensible at k = 0, where the textbook "normal approximation" gives a zero-width interval. Example from the report: 29 of 80 gives 0.3625 with interval 0.2657 to 0.4719. The repository test checks k = 2, n = 10 against the hand calculation 0.0567 to 0.5098.



  
Wilson interval

  

    
    
  

  




Honest limit
Wilson intervals assume independent trials. Our samples are not independent: five samples share a task and a model, and tasks differ enormously (0% to 100% biased). The intervals in this guide and in REPORT.md are therefore optimistic. The paired task-level tests below respect the clustering better.



9.5 Comparing prompts: paired contrasts


To ask "does the repair prompt lower bias?" we pair each task with itself. For each task and model we compute the bias rate under detailed (before) and under the other variant (after), and take after − before. The report gives the mean difference over tasks, a bootstrap interval and a sign-flip p-value.


    
  
  • Paired bootstrap: resample the per-task differences with replacement 10,000 times; the 2.5th and 97.5th percentiles of the resampled mean are the interval.
    • 
  
  • Sign-flip test: under the null that the prompt does nothing, each task's difference is equally likely to be positive or negative. Randomly flip the signs 10,000 times and count how often the flipped mean is at least as extreme as the observed one. Zero differences contribute nothing.
    • 



Worked example

Four tasks have differences −0.4, −0.2, −0.2, −0.6. The mean is −0.35. Sixteen sign patterns are possible; only the all-negative and the all-positive pattern give a mean as extreme as 0.35 in size. So the two-sided p-value is 2/16 = 0.125. Even though every task improved, four tasks can never give p below 0.125.



9.6 Many comparisons: Holm


For each model the report tests eight related contrasts: overall direct mitigation, direct mitigation on each of six attributes, and overall feedback repair. Self-review is reported but outside the family. Holm's step-down rule: sort the p-values smallest first; compare the smallest with α/m, the next with α/(m−1), and so on; reject until the first p-value that misses its threshold, then stop. With α = 0.05 and m = 8 the first threshold is 0.00625.

9.7 Why "Holm does not reject" is not "no effect"


This is the subtlest point in the statistics and a likely interview probe. A sign-flip test over 16 tasks can only be as strong as the number of tasks whose rate actually changed. Exact two-sided p for m non-zero differences that all point the same way is 2/2m. The strictest Holm threshold here is 0.00625, so a contrast needs at least nine non-zero, same-direction tasks (2/512 = 0.0039; eight give 0.0078, which fails). I counted them from the saved data.

11.7 Extraction failures and the GPT-OSS truncation


The four OpenAI models extracted a function from every reply. GPT-OSS 20B did not: 164 of 560 (29%) failed, 117 with parse_error and 47 with wrong_name, concentrated in the role variant (40 of 80 extracted) and the baseline (57 of 80). In 161 of the 164 failures the generation ended at exactly 800 tokens, the max_tokens cap. The wrong_name replies I inspected were empty strings. The pattern is consistent with a reasoning model spending its token budget before or while writing code: a truncated reply is a parse error, an empty one has no function.


Why this matters for the science

GPT-OSS's low baseline rate (22.8%) is computed on 57 of 80 samples, and the missing 23 may not be missing at random. The simplest fix is to raise max_tokens for reasoning models and re-run only the failed ids; the resume logic makes that cheap. Until then, do not rank GPT-OSS against the others without this caveat. I read the 800-token coincidence off the saved token counts; I did not re-run any model to test it.


Llama 3.2 3B: 214 saved, 183 extracted, all 31 failures parse_error; none of its 31 terse samples parsed.



11.8 Proxies


In the detailed_proxy variant the six protected keys are replaced by zip code, first name and native language. Pooled over the five models, 94 of 375 executable functions (25.1%, Wilson 20.9 to 29.7%) changed their output on at least one proxy. By proxy: zip code 58 of 375, native language 58 of 375, first name 0 of 375. The zip-code set and the language set overlap in only 22 functions. By model, the share changing on at least one proxy is GPT-4.1 nano 49/80, GPT-OSS 15/55, GPT-4.1 mini 15/80, GPT-4o mini 9/80, GPT-4o 6/80.


These are descriptive. They are not bias rates and are outside every statistical family, because a zip-code effect is not a race effect unless we can show the link, and we do not. The striking observation is that no function ever reacted to first name. Models appear willing to use geography and language but not names, which may reflect training on "never use name" advice. That is a hypothesis for a follow-up, not a result.



11.9 How blunt the bias is


Among the 217 baseline violations, the output changed on an average of 77.8% of the testable profiles, and in 70.5% of them it changed on every profile. The rules are blunt: a hard-coded +5 for disability, +100 for age over 60. They are not rare edge cases, which is why 24 profiles are enough to catch them.

12.2 The most important critique of the mitigation result


The direct prompt lists the exact six names. The test varies exactly those six fields. A model that stops reading them passes. This is close to measuring a prompt against its own target, a Goodhart-style risk. Two things the data cannot say:


    
  
  • Displacement. Did the model move the same preference to something correlated, such as a proxy? We tested proxies only in a separate prompt where protected keys were absent, and 25% of those functions changed on zip code or language. We never combined the direct instruction with the proxy keys. That experiment is the natural next one (Section 14).
    • 
  
  • Quality. We only have the thin sanity relation. A function with fewer inputs may be less accurate for legitimate reasons, which is a fairness-accuracy trade-off the project does not quantify. Sun et al. measured a real quality drop under reasoning.
    • 




12.3 Why might our direct-prompt result differ from earlier papers?


Huang et al. report that direct prompts only partly worked, and Ling et al. report that chain-of-thought and persona prompts raised bias. Chen et al. found that a prompt naming the protected attributes drove their CBS to zero, as ours did. Possible reasons for the spread, all untested:


    
  
  1. Model generation. We used newer models.
    2. 
  
  2. Signature design. Our protected keys are explicit, finite, and in the docstring, so "do not use X" is easy to follow. Solar passes a self object whose attributes the model has to choose from, and Huang et al. let the model pick parameters.
    3. 
  
  3. Prompt content. Ours names the six attributes verbatim; so do Huang's zero-shot and Chen's bias-awareness prompts. Ling's CoT prompt does not name them ("ensure fairness"). Naming looks like the ingredient that matters.
    4. 
  
  4. Measurement. A different bias detector, tasks and temperature would all shift rates.
    5. 




12.4 What would make the result stronger


    
  
  • A label-sensitivity sweep that re-scores the saved code under alternative label tables (no model calls needed).
    • 
  
  • A displacement test (mitigation prompt plus proxy keys).
    • 
  
  • A larger and more varied task set, so contrasts have enough non-zero tasks to clear Holm.
    • 
  
  • A harm-direction analysis, and a small human labelling study of flagged functions.

13. Limits and known issues


A good interview answer to "what are the weaknesses?" is specific and already known. This is the list, grouped by the kind of validity it threatens.



13.1 Construct validity: does the test measure what we say it does?


    
  
  • Difference is not harm. Any output change on an invariant attribute counts, whether it hurts or helps the protected group.
    • 
  
  • Labels are decisions. Insurance, benefits and medical age and disability cells are invariant "by default". Only credit × age is exempt.
    • 
  
  • Counterfactual realism. We change one field and hold the rest fixed. In real data, age, disability and other features are correlated. Our profiles draw features independently.
    • 
  
  • Only explicit attributes. Bias via proxies is logged but not scored, and combined effects are untested.
    • 
  
  • Prompt priming. The protected keys appear in the prompt. A real developer might not hand the model those columns.
    • 




13.2 Internal validity: are the numbers right?


    
  
  • Defaults as the background. Every pair holds the other five protected fields at their first grid values (woman, Black, age 22, Christian, no disability, single). Interactions with other values are untested.
    • 
  
  • The grid can hide branches. Ages 22, 35, 47 and 68 only; thresholds elsewhere are invisible.
    • 
  
  • Executable-only denominator. Models that fail more often are scored on fewer, different samples.
    • 
  
  • Static scan limits. No computed keys, getattr, nested helpers or exec.
    • 
  
  • Single temperature, single run, unpinned versions. We did not store provider system fingerprints, so a model alias may map to a different snapshot later. Runs finished by 10 Oct 2026.
    • 




13.3 External validity: does it generalise?


    
  
  • Sixteen tasks, Python, single-function, US legal framing, English prompts.
    • 
  
  • Five hosted models from two vendors. No Anthropic or Google model finished. Open-weight models (Llama, Qwen) are missing, so no conclusion about open code models.
    • 
  
  • Synthetic people. No relationship to any real population.
    • 




13.4 Statistical validity


    
  
  • Wilson intervals assume independent trials; our samples cluster by task and model, so they are too narrow.
    • 
  
  • Task-level paired tests have little power when few tasks change (Section 9.7).
    • 
  
  • Pooled rates sum models with different executable counts.
    • 
  
  • A better model would put task and model as random effects (a mixed-effects logistic regression) and report effect sizes with honest uncertainty.
    •

Why does fairness of generated code matter when we already audit model text?


Because code turns a model's tendencies into rules that execute silently on every case, and the code outlives the chat. People also review generated code for correctness more than for fairness. Text-bias benchmarks (BBQ, StereoSet, CrowS-Pairs) look at words; in code the bias is a branch such as if age > 60. Huang et al. and Ling et al. showed bias in code even from models trained to avoid biased text.



What is the research question and what is your contribution?


How often does LLM-written decision code depend on protected attributes, which attributes and tasks, and which cheap mitigations work? The contributions are a reproducible harness with a pre-registered label table, a fixed-signature benchmark of 16 tasks, a sanity check so mitigations cannot cheat, a static versus dynamic comparison, careful denominators, a paired statistical treatment, and a first look at self-review and feedback repair on current hosted models. I would be careful to call it an empirical replication-and-extension study, not a new fairness theory.



How is this different from Huang et al. (TOSEM 2025)?


Same core definition and metrics, different setting. They used 334 one-sentence prompts where the model chooses the parameters, 5 older models at temperature 1.0, and AST-derived tests with manual review of unclassifiable code. We fix the signature, use 16 curated tasks with legitimate-feature lists and sanity relations, exempt credit×age on legal grounds, log proxies separately, report executable-sample denominators with Wilson intervals and Holm-corrected paired tests, add a self-review arm without feedback, and test newer models. I cannot claim our percentages replicate theirs, only the definitions and the direction of the mitigation effect.



How is it different from Solar (Ling et al.) and FairCoder (Du et al.)?


Solar uses a class-based task with typed attributes and generated metamorphic tests across 343 tasks; FairCoder uses scoring functions and unit-test generation with a static detector and FairScore. Our unit test is the same metamorphic relation as Solar's, but over a smaller, hand-labelled task set with explicit legal-use labels and a statistical comparison across prompts. We do not do unit-test generation or direction-of-bias scoring yet; both are natural extensions.



Why a fixed signature? What does it cost you?


It makes testing fully automatic and puts all models on the same footing; free-form prompts need AST inference of parameters, which sometimes fails. The cost is realism and priming: the keys are listed, so the model is shown protected data it might not otherwise see. That makes our baseline a measure of "what the model does with protected inputs in hand". The Glasgow paper shows that forcing models to use every attribute inflates bias, which is a related effect.



How do you decide which differences count as bias?


A label table of 96 (task, attribute) cells, written before any model call. Credit×age is may_legitimately_differ because Regulation B permits age in an empirically derived credit system and allows favouring the elderly. Every other cell is invariant; where a statute was consulted it is cited, and where none was, the file says so. Proxy differences are saved but never counted. The weakness is that the default for cells like medical priority is a judgement, so I would run a sensitivity sweep over alternative tables.



Why synthetic profiles, and why 24?


Synthetic data avoids privacy issues and is deterministic with seed 42. There is no power analysis behind 24; it is a pragmatic size. The data suggest it is adequate for blunt rules: when a violation exists, the median function changes on most profiles (mean 78%, and 70% of violations change on all 24). It is inadequate for rules that fire only for rare feature values or thresholds the age grid skips, so a finer grid is a planned extension.



Why temperature 0.8 and five samples?


The CBS_U and CBS_I metrics need variability across samples; at temperature 0 five samples would be nearly identical. The papers use 1.0; 0.8 is a compromise, and Groq rewrites a literal 0. Five samples per prompt follows Huang et al. Ling et al. found bias can move a lot with temperature (CodeLlama 28% to 65% as temperature fell), so a single temperature is a limit I state.



Why run both static and dynamic analysis?


They fail differently. Reading code can flag a dead reference (89 cases here, e.g. a branch no profile reaches). Running code cannot see branches the grid does not trigger. Keeping both lets us check one against the other; in 2,169 cells the scanner never missed a dynamic violation, which supports it as a cheap pre-filter. I would not claim that it generalises beyond this task format.



What is the sanity relation for?


A degenerate "fix" such as returning False for everyone is perfectly invariant. Each task has a monotone check (for example more income must not turn an approval into a rejection), reported next to every bias number. Pooled, 0 of 354 baseline functions failed it, and failures appear under terse (6), direct (5, all GPT-4o mini), role (2) and repair (1). It is a thin check, one feature per task, and bail has none.



Is your sandbox safe?


It is a guard against accidents, not an adversary: a subprocess with an empty environment, 13 allowed imports, a builtins allowlist, CPU and file limits, and a per-call alarm. The builtins list still includes getattr, so it is not an escape-proof jail, and the README says so. For a production audit tool I would use containers or a seccomp-based runner.



Define CBS, CBS_U@K and CBS_I@K, and say how your headline differs.


CBS is biased functions over generated functions. CBS_U@K is the share of prompts with at least one biased sample of K; CBS_I@K the share where all K are biased. Our headline is biased over executable functions, which equals Ling et al.'s CBS definition, whereas cbs_at_k in the code keeps non-running samples in the denominator as "not biased". For GPT-OSS on disability, 12 biased gives 0.15 on the 80 planned samples and 0.21 on the 57 that ran. I always state the denominator.



Why Wilson intervals?


They behave at small counts and near 0 or 1, where the normal approximation can give zero-width or out-of-range intervals. We have many 0-of-n cells. Their weakness is the independence assumption, which our clustered samples violate, so I would call them optimistic and prefer cluster-aware methods for confirmatory claims.



Why a sign-flip test and bootstrap instead of a t-test?


The unit is the task (16 of them) and the outcomes are bounded rates with many zero differences, so normality is doubtful. A paired sign-flip test makes no distributional assumption beyond symmetry under the null; the bootstrap interval is a distribution-free description of the mean change. Solar used two-sample t-tests; I think pairing by task is more appropriate.



Explain Holm, and why GPT-4o's improvement is not "significant".


Holm controls the family-wise error rate across the eight related contrasts for each model by comparing sorted p-values with 0.05/8, 0.05/7, and so on, stopping at the first failure. For GPT-4o, seven tasks moved, all toward less bias, p = 0.017, which does not beat 0.00625. With only seven non-zero tasks the exact sign-flip p is 2/128 = 0.016, so no outcome could pass the first threshold; at least nine same-direction tasks are needed. "Not rejected" means underpowered, not "no effect".



What is your unit of analysis, and is there pseudo-replication?


For headline rates the unit is a generated function; for contrasts it is a task. Functions from the same task and model are correlated, so pooled intervals are too narrow; that is why the contrasts use task-level means. A mixed-effects logistic model with random effects for task and model would be the principled upgrade.



Give me the findings in 30 seconds.


About 32% of baseline functions that ran are biased on at least one invariant attribute, with models between 23% and 43%. It is age (30%), disability (27%) and marital status (7%); gender and religion are zero. It concentrates in support and medical priority and insurance. A direct instruction brings it to zero, test-feedback repair to 1.9%, and self-review to 9.9% with large model differences.



Why is gender bias zero but disability bias high?


We did not test causes. A plausible reading, consistent with Du et al. and Chen et al., is that models have learned strong norms against using gender, race and religion in decision logic but treat age and disability as relevant to risk, need or urgency, so they add points. Our task pattern fits: highest in queues, premiums and benefits. A labelled harm-versus-benevolence analysis would be needed to say more.



Your direct-prompt result is 0%. Isn't that too good?


It is surprising next to Huang et al., where direct prompts only partly worked, and it agrees with Chen et al.'s bias-awareness prompt. The static scan shows the mechanism: after the instruction, none of 373 functions reads a protected key. The caveat is circularity, since the prompt names the same six fields the test varies, and we did not test displacement onto proxies. So I would say the instruction removes explicit use, not necessarily all unfairness.



Why does feedback repair work better than self-review?


Feedback tells the model which attribute changed the output on how many profiles, which is information it may not extract from reading its own code (Huang et al. found models detect few of their own biases). Pooled, feedback leaves 1.9% biased and self-review 9.9%, though GPT-4o, GPT-4.1 mini and GPT-OSS fix themselves almost fully without feedback, while GPT-4.1 nano does not (30% remain).



Are larger models fairer?


The data do not support that. GPT-4o mini (36%) is above GPT-4o (31%), GPT-4.1 mini (25%) is below it, and intervals overlap. Huang et al. also found GPT-4 had higher age bias than GPT-3.5-turbo. Model scale is confounded with provider, training and sampling behaviour.



What did the proxy experiment show?


With protected keys removed and proxies offered, 25% of functions still changed on zip code or native language (58 each of 375), and none ever on first name. Those are not bias rates: linking a zip effect to race needs evidence we do not have. It shows that removing protected columns does not make the output independent of correlated features, which is the classic failure of fairness through unawareness.



What is the biggest weakness of this work?


Construct validity: a flagged difference is not a harm, and several labels (medical, insurance, benefits age and disability) are defaults. If those cells were exempt the headline would drop. I would quantify that with a label-sensitivity sweep and a small human audit. Second, GPT-OSS lost 29% of samples to token truncation, and third, the direct-prompt result is measured by the instrument it targets.



Could a "violation" actually be good?


Yes. A priority queue that adds points for a disability may be benevolent; an insurance function that adds $200 for the same attribute is the opposite. The current test flags both. I would add a direction analysis (does the protected value raise or lower the output, and for whom) and report harm and benefit separately.



Is this reproducible?


Partly. Seeds, profiles, config and code are fixed and tests are offline, but the results live in gitignored JSONL files that must be copied by hand, hosted models are aliases without recorded fingerprints, and API seeds are best-effort. Scoring is fully reproducible from the saved replies; regeneration is not guaranteed.



What bugs did you find in your own work?


Four that touch numbers or prompts (I have since fixed three in code and regenerated the summary; GPT-OSS truncation remains open): the per-attribute rate in summary.csv includes exempt cells in the denominator (understating age); repair prompts for 23 non-executable GPT-OSS samples say "no violation observed"; GPT-OSS replies are cut at 800 tokens; and one e2e test fails because it mocks the global sleep. None changes the headline findings, and all are fixable. Saying this unprompted shows how I audit my own pipeline.



If you had a year, what would you do?


1) A label-sensitivity and human-audit study to separate harmful from benevolent differences. 2) A displacement experiment combining mitigation with proxy keys. 3) Directional analysis and intersectional pairs. 4) A mixed-effects reanalysis on a larger task set. 5) Extend from single functions to multi-file projects and agentic tools, where fairness checks could run in CI. 6) Study how reasoning budgets affect bias, following Sun et al.



How would you mitigate beyond prompts?


A tool-level approach: run the metamorphic test automatically after generation and loop the failing pairs back (this is our feedback arm, and it is the most effective), or use a static check in the editor or CI. At the model level: fine-tuning or preference training with counterfactual pairs, though Du et al. found BBQ-based post-training did not help much. At the process level: multi-agent roles that scope allowed attributes, as in Rabbi et al.



How does this connect to regulation and practice?


Hiring, credit, insurance, education and benefits are domains where many jurisdictions regulate automated decisions and where anti-discrimination law applies. Our label table uses US sources as research categories. A tool like this could support pre-deployment auditing of generated code, but compliance would need deployment context and legal review, which this project does not provide.



"Isn't this just unit testing?"


It is metamorphic testing, which is unit testing without an oracle. The scientific content is in what to test (which attributes and labels), how to sample (profiles, temperature, samples), how to count (denominators, exempt cells), and how to compare interventions with honest statistics.



"Your test only catches explicit use. What about learned proxies?"


Correct. We test the named attributes and log three proxies separately. A model could keep the same preference through correlated features. Testing displacement and learned proxies in realistic correlated data is a stated next step.



"Why not use an LLM to judge bias in the code?"


Execution is deterministic and has no false positives for the relation we define, which is why Huang et al. and Ling et al. prefer tests to classifiers. LLM judges can be noisy; in Sun et al. GPT-5.1 matched human labels at about 82% accuracy for reasoning traces. A judge could complement the test for semantic questions (is this justified by the task?), validated against human labels.



"Can you really change one attribute and hold everything else fixed?"


In a function call, yes, which is what makes the test clean. In the world, no: age, disability and income are causally entangled, and a counterfactual person who is "the same except disabled" may not exist. So our result is about the function's dependence on an input, not about a causal claim over real people. This is a known conceptual limit of counterfactual fairness.



"Your categories are binary or fixed lists. Is that fair?"


The lists are a test grid, not an ontology: three gender values, four race values, and a binary disability string. Real attributes are richer and often continuous. A larger grid and a function-level property test (sweep age across a range) would be better, and I would say so rather than defend the lists.
